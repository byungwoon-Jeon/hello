# Python 문서 처리 자동화 프로젝트 규칙 (템플릿)

> 프로젝트별 실제 구조·Python 버전·테스트 명령을 확인하고 필요한 항목만 유지한다.
> 이 템플릿이 실제 프로젝트에서 자동 적용되려면 파일을 프로젝트 루트에 배치해야 한다.

## 목적

- Python 기반 문서 처리, OCR, LLM 추출, 데이터 파이프라인 코드의 안전한 개발·유지보수
- 기존 인터페이스 호환성과 재현 가능한 검증을 우선
- 요청하지 않은 대규모 재설계나 리팩터링 최소화

## 프로젝트 탐색

- 먼저 README, 의존성 설정, 진입점, 호출 관계, 입출력 스키마를 읽는다.
- 실행 환경과 실제 Python 버전을 확인한다. 버전을 추측하지 않는다.
- 네트워크·DB·운영 API 접근이 필요한 작업은 실행 전 목적과 영향을 설명한다.

## 코딩 규칙

- 기존 파일 구조, 이름, 스타일, 데이터 포맷을 존중한다.
- 가능한 경우 함수 입력은 `in_params` 하나의 딕셔너리로 정리한다. 기존 함수가 다른 계약을 사용하면 허락 없이 바꾸지 않는다.
- DB에서 읽은 한 행은 `record`로 명명한다.
- OCR/LLM 파싱 결과의 키, 타입, 누락 필드 규약을 임의로 바꾸지 않는다.
- 정상·실패 결과를 구분하고 원인 파악 가능한 오류 정보를 유지한다.
- 불필요한 추상화, 전면 리팩터링, 신규 의존성 추가를 피한다.
- 실제 코드에서 확인하지 못한 내용은 사실이 아닌 추정으로 표시한다.

## 분석 → 수정 → 검증

1. 증상 또는 요구사항과 관련된 파일/함수를 찾는다.
2. 입력 → 전처리 → 추출 → 후처리 → 저장/반환 흐름을 추적한다.
3. 수정 후보와 영향받는 호출자·데이터 계약을 명시한다.
4. 변경 계획이 확정되기 전에는 읽기와 분석만 수행한다.
5. 승인된 범위에서만 수정한다.
6. 관련 테스트를 실제로 실행한다. 실행할 수 없으면 이유를 적는다.
7. 변경 파일·검증 결과·남은 위험을 보고한다.

## 검사할 예외 케이스

- 빈 입력, 파일 없음, 손상된 파일, 입력 포맷 차이
- OCR 실패, 누락된 필드, 낮은 인식 품질
- LLM의 JSON 파싱 실패, 예상과 다른 데이터 타입·키
- 타임아웃, 일시적인 API 실패, 재시도 및 중복 처리
- DB 오류, 트랜잭션·중복 키, 부분 실패
- 기존 출력 CSV/JSON/파일명 규칙과의 호환성

## 보안 및 운영

- 운영 DB 쓰기·배포·삭제·대량 처리·네트워크 전송은 사용자 승인 없이 실행하지 않는다.
- 인증정보, 고객 문서, 개인정보, 내부 API URL을 출력하거나 외부 서비스로 전송하지 않는다.
- 민감 데이터가 필요한 테스트는 허용된 가명·합성 데이터로 대체한다.
- 수정 전 Git 작업 트리 상태를 확인하고 기존 사용자 변경사항을 보존한다.
- Git reset --hard, 강제 push 등 복구가 어려운 명령은 실행하지 않는다.
